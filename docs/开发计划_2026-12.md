# 开发计划与排期（2026-12 起，12 周到公测）

**起点**：原型 v2.3
**目标**：12 周后交付 **PWA 版 1.0**（可安装到主屏、可离线、可分享链接），原生壳延后
**关键调整**（本版）：
1. **数据导入提前到 P3**（W4–W6），不再放最后——用户懒得手填十一年，导入决定留存。
2. **先做 PWA，不做原生**——省掉 App Store 与 TestFlight，分发改成链接 + 添加到主屏。

**假设**：单人 + AI 辅助。加一名前端可压到 9 周。

## P1 · 数据底座（W2–W4）

**选型**：Supabase（Postgres + Auth + Storage）。

| 任务 | 说明 | 周次 |
|---|---|---|
| 数据模型 | users / film_blocks / records / projects / orders | W2 |
| 账号 | 邮箱 magic link；匿名账号可升级且资产不丢 | W2 |
| 本地数据迁移 | 首次登录合并 localStorage，冲突按时间取新 | W3 |
| 离线缓存 | IndexedDB 先读后同步 | W3 |
| 导出 / 删除 | JSON 导出，账号删除 24h 内清空 | W4 |
| 行级安全 | RLS，一条记录只属于一个人 | W4 |

**验收**：两台设备登录 → 底片一致；删除账号 → 24h 内不可恢复。

## P3 · 数据导入（W4–W6）★ 提前

这是留存的分水岭：让底片在打开的第一分钟就有内容。

| 任务 | 说明 | 周次 |
|---|---|---|
| 相册导入 | 选照片 → 读 EXIF 拍摄时间 → 按年归入年份块 | W4–W5 |
| 日历导入 | 接日历事件（读书会、出差、发布会），提取年份与事件 | W5 |
| 简历导入 | 上传 PDF/图片 → 抽取公司与任职年份 | W5–W6 |
| 导入预览与确认 | 先给「将写入 2018 年 3 条」的预览，用户确认才落库 | W6 |
| 去重与冲突 | 同一年同一事件只留一条 | W6 |

**验收**：导入 200 张照片，5 秒内完成归年；用户可逐条撤销。

**注意**：相册读取必须在端上完成（EXIF 本地解析），照片**不上传**——这既是隐私要求，也省流量。

### iOS PWA 的两个硬限制（必须写进产品说明）

1. **存储可能被清理**：iOS 对 PWA 的 Storage 有配额，长期不用可能被清除 → **云端为准**，本地只做缓存。
2. **安装方式不直观**：必须在 Safari 里「分享 → 添加到主屏」，微信内置浏览器不支持。引导文案要写清楚。

## 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| iOS 存储被清理 | 用户以为数据丢了 | 云端为准 + 明确的「已同步」状态 |
| 相册权限被拒 | 导入走不通 | 保留手动补记与简历导入两条后备 |
| P1 是关键路径 | 晚一周全线顺延 | 先做最小可用（登录 + 同步），导出后置 |
| 春节（2/6 前后） | W11 效率下降 | 已在 W12 留一周缓冲 |
| 单人排期 | 病假即延期 | P5 的动效与无障碍可裁剪 |
